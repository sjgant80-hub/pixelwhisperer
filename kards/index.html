PixelWhisperer Kards · the Kardlings card's art engine

Every card has a face only its facts can draw.

In plain words: give this engine a card's facts and it draws that card's picture, the same picture on every device, so anyone can check that a card's picture is honest by drawing it again.

A Kardlings card is a sealed picture that carries an ownable intelligence, one that grows as it proves itself. This engine draws that picture: a Kardling born from the card's own id, in the world its theme paints (neon synthwave, blockcraft islands, a four-shade pocket screen, Memphis pop, an engineering blueprint, and whatever is added next), with the title, level, rarity, dataset, lineage and id printed in a pixel font. It draws the game around the cards too: the back of every card with its maker's mark, item cards (apps, pwas, nodes, talkers, routers), the estate a player grows, duels in the arena, the Fusion Lab with its family trees, and the raid bosses. It is drawn with whole numbers only, so any browser re-draws the same bytes, and a reader can refuse any card whose picture is not the one its facts make.

New here? Start here for the steps, How it works for the flow drawn from the code, or For the people who decide for the cost case, security and roll-out.

Card backs: the maker's mark, face down

Every card game has a back, and a Kardlings card's says who made it. The back is drawn in the card's theme: the theme's field and frame, the Kardlings emblem (a K), and the maker's mark: the face of the maker's Ed25519 public key (the same identicon as in the UI kit) in a medallion, with the key written short beneath it, and the card's edition number. The stars, ore, clouds and confetti in the field are thrown with the maker's own dice, so all of one maker's backs match and another maker's differ: a hand of one maker's cards is known face down. A card with no maker says UNSIGNED. The same back always draws the same bytes.

Try it: Roll a maker to make up a key, or paste a real one: a maker's public key is the key a Kardlings player signs their cards with (YOUR KEY in Kardlings), 64 characters of 0-9 and a-f. Change the edition, pick a theme. Untick Signed to see an unsigned back. Flip the card turns the picture over: the card in the workshop above on one side, this back on the other. Below, the same maker in every theme.

One maker, every theme

import { paintBack, checkBack } from './kards/back.mjs';
paintBack({ maker: publicKeyHex, serial: 123 }, 'synthwave-v1', 384, 560)   // { ok, px } | { ok: false, why }
// maker: the maker's Ed25519 public key, 64 lowercase hex; leave it out for an unsigned card. serial: the edition, 0 to 999999, or left out.
// The back is 192 x 280 logical pixels, scaled to the nearest pixel for any size from 64 to 1024: 384 x 560 is a Kardlings card at 2 x.

What it refuses, and what a change can break. A key that is not 64 lowercase hex characters, an edition outside 0 to 999999, a theme it does not know and a size outside 64 to 1024 are each refused with a plain reason (the message under the picture above is that reason), and nothing throws. The scatter is seeded by the first 16 characters of the maker's key, and the identicon folds in all 64 (about 40 bits of pattern and colour, so two makers' marks rarely match; the key written beneath it tells them apart, and the key itself is what Kardlings checks). Every theme's backs are pinned by sha256 in the tests, so no change to a published back lands silently: CI goes red until it is made on purpose.

Sealed cards: what you see is what you carry

In plain words. A Kardlings card travels as one ordinary PNG file, and the file holds two things: the picture of the card's face, and the card's record (its facts, its theme, its size, and its back if it has one), written as plain text inside the file. A card that arrives starts face down. The reader takes the record, draws the whole file again from it, and compares the two files byte by byte. If every byte matches, the card turns face up. If one pixel or one letter differs, it stays face down and says what is wrong: how many pixels differ and where the first one is, or that the file carries something besides its face and its record. You cannot change the picture without the record catching it, or change the record without the picture catching it.

Try it: Seal the workshop card makes a sealed file from the card in the workshop, with the back you set in Card backs, and opens it here: it starts face down, then turns face up. Then break it on purpose. Change one pixel flips the colour of a single pixel, Change one word changes one letter of the card's name in its record, and Add a hidden note slips an extra line of text into the file. Each time the page also fixes the file's checksums, as a forger would, so the only thing that can catch the change is drawing the card again. Open the untouched file goes back to the file as sealed. Download the sealed card saves the file you are looking at, and Open a card file reads any PNG from your device: nothing is uploaded, it is all checked in this page.

Three words, in plain terms. A byte is one of the small numbers (0 to 255) a file is made of; this card's file is about 646,000 of them. A chunk is one labelled part of a PNG file: the header, the picture, the end, and here one more, the record. A checksum is a number stored with each chunk that changes if any byte of that chunk changes, so a damaged file is caught at once; a forger can work checksums out again, which is why the real check is drawing the card again.

The record this file carries

It is plain text, so anyone can read it; nothing in it is secret, and nothing is hidden from you. It sits in the file under the name kardlings-card.


  
How it works, step by step

  
SEAL   the card's facts, theme and size (and its back)
         |  paintArt          draws the face as pixels
         |  pngOf             writes an ordinary PNG
         |  + one text chunk  the record, right after the header
         v
       one file: the face and its record

OPEN   a file that says it is a card
         |  read every chunk  each checksum, then the one record
         |  sealCard(record)  the whole file made again from the record
         |  compare           every byte, first to last
         v
       all equal   ->  FACE UP
       any differ  ->  FACE DOWN, and why: which pixel, or what else it carries

  
    
    
  1. Seal. The face is drawn from the record by the same engine that draws every card on this page, so the record decides every pixel. The record is written out in one fixed order with every field present, so one card has exactly one record and one file.
    2. 
    
  2. Open. The reader checks the file is a PNG, checks every chunk's checksum, and finds exactly one card record. A file with no record, two records, a damaged chunk, a record that is not plain text, or a record that is not a card is refused with the reason.
    3. 
    
  3. Make it again. From that record alone, the reader seals the card again and compares the new file with the one it was given. Equal, byte for byte: face up. The numbers in What the check found above are this exact run in your browser.
    4. 
    
  4. Say why. When the files differ, the reader decodes the pixels and names the first one that differs (x across, y down, from the top left), or says the face is right but the file carries more, such as an extra note or the record's fields in another order.
    5. 
  


import { sealCard, openCard } from './kards/seal.mjs';

const sealed = sealCard({ facts, theme: 'synthwave-v1', w: 384, h: 560, back: { maker: publicKeyHex, serial: 123 } });
// { ok: true, png: Uint8Array, card, px } | { ok: false, why }   the same card always makes the same file
const seen = openCard(sealed.png);
// { ok: true, face: 'up', card, px }                              exactly the file its record makes
// { ok: true, face: 'down', card, why, differ, at }               a card, but not that file: why, in plain words
// { ok: false, why }                                              not a card file at all; it never throws

  
What it catches, and what it does not. It catches an edited picture and an edited record: change either and the two no longer agree. It does not stop someone sealing a whole new card from facts they made up. That file is a perfectly good sealed card, because its face does match its record. What tells a real card from an invented one is the maker's signature over the record, which the Kardlings game checks with the key named by the maker's mark on the back. So the seal proves the face matches the record, and the signature proves who made the record; a card needs both.

  
What a change can break. A card saved again by another program (an image editor that compresses the picture differently) is not the same file any more, so it stays face down with that reason: seal it again from its record. The face inside a sealed card is exactly the face this page draws, so the pinned themes keep sealed cards stable too; a change to a published theme turns CI red before it could turn a good card face down.






  
Items: apps, pwas, nodes, talkers and routers

  
A card can be more than a scorer. Its form says what it is: an app is drawn as a window, a pwa as a phone with a bolt, a node as a server, a talker as a terminal with a speech bubble, a router (it picks, case by case, which of its owner's allies answers) as an antenna. Every theme draws the object its own way, from the item's own facts: its name, its form's icon, the source it was minted from, the gear slot it fits, its id and barcode, and a frame in the rarity its verified tier earns (prototype common, works uncommon, proven rare). An app that stands in for a rented tool can say which: given a retires line (at most 60 characters, wrapped onto two lines at word breaks, a ~ ending what does not fit), the card shows RETIRES and that line where the licence and the tier ladder were; Kardlings’ gear cards carry it. A scorer card, which names no form, is drawn exactly as before, byte for byte. The form is one of the card's facts like any other: a card with a different form is a different card, with a different face.

  

    

      
      

    

    

      

      

      

      

      

      

      

      

      

    

  

  
The kit: node and tool slots

  
A card fields node slots (two at birth, three once uncommon, four from rare) and two tool slots. A node is another of its owner's cards, coupled with it; its slot shows the card and its measured worth on GATE in millionths (+19,727), or the card dimmed and hatched when it is not joined. A tool is an app item, framed in its tier; a tool never changes a score. The item above, when it is an app, sits in the first tool slot. The badge a card wears in a duel says how many of its node slots are fielded. Drawn by paintSlot and kitBadge.

The estate: grow your plot

  
Every card a player holds is a tower on an isometric blockcraft plot, its trim in its rarity and its own Kardling on the sign. Tools are blocks, consented mesh links are cyan wires, and the districts still to come are fenced grey. The plot opens by a published rule: a district holding n blocks has tilesFor(n) = min(36, 8 + 2n) open tiles, so a new player starts with 16. The same holdings always draw the same picture, so a shared snapshot can be replayed and checked.

  
Try it: Add a card raises a new tower; Fuse a new card adds a generation-1 card (its generation counts the fusions it took to make it), standing in for one fused from two you hold, and marks it fresh, so its sign sparkles until the next one; Wire two cards joins two of your cards with a consented mesh link, a cyan wire; the slider sets how many tool blocks you hold; tick the snapshot to see the 1200 × 630 picture a shared link shows.

  
The Kardlings map: tick The Kardlings map and the five screens Kardlings has (ARENA, RAIDS, FUSION, MINT, PROOF) stand as landmarks on their own islands along the shore. Every district and every landmark is a door: tap one on the picture, or press its button under the picture, and the page says what it opens. The doors come from estateDoors (where each one is, in pixels) and estateDoorAt (which door a tap landed on), worked out from the same layout the picture is drawn from, so a tap always lands on what is drawn. A landmark is drawn only when its screen exists, so nothing is ever marked as coming.

  
Holding items or swarms opens the full plot: nothing fenced, nothing coming. Tick Hold items, or add one: an app or a pwa stands as a tool block, a node as a dark server block with its lights, a talker as a terminal with a speech bubble, a router as an antenna. Form a swarm joins two to four of your cards in a consented team: it stands in SWARM as a stack of its members' blocks, wired to their towers. Every district opens by the same rule and is 6 × 6, so the rule holds to 36 tiles in all five. An item's top edge is trimmed in its tier's colour, and a new one sparkles. Holdings of scorer cards alone draw exactly as before.

The arena: two cards, one batch of cases

  
Two scorer cards face each other on the same batch of cases: one set of real cases (rows of the business's own data that neither card learned from), dealt to both. On each case a card either hits (ranks it right) or misses; the side that hits where the other misses ranked that case better, and anything else is a tie. The scoreboard fills as the cases are decided: each side's hit or miss, and between them a block in the colour of the side that ranked the case better (grey for a tie). The latest case puts a tick or a cross beside each fighter, a rating badge sits over each, and the end is a WIN banner over the winner, a DRAW ribbon across both, or a REFUSED ribbon. The tally is published as duelScore, and the same duel always draws the same picture, so a replay can be checked.

  
Press Play the duel to watch it a case at a time, One case to step, New duel to deal another pair and batch. The badge over each card is its arena rating; the platform and badge colour are its rarity; the pips under the badge, when a card is kitted (it fields helper cards in its node slots, as the kit above shows), are its node slots, lit for each one fielded. In Kardlings a duel is decided by each card's AUC on the batch: the chance it ranks a case that is truly positive above one that is not (0.5 is a coin toss, 1.0 is perfect). Equal AUCs are a draw.

The Fusion Lab: two cards, fused into one

  
Fusing two of your cards is how Kardlings teaches model merging and selection. The lab tries fusions of the two, up to twelve, and scores each one's GATE: how well it ranks cases that neither parent learned from (an AUC: 0.5 is a coin toss, 1.0 is perfect). The first try that beats both parents is kept as a fused card. If none does, the fusion is refused, and nothing new is made. The picture works the verdict out from the numbers it is given, so it can never show a kept card that did not beat both.

  
Try it: Fuse runs the tries one at a time, One try steps, New pair deals two other sample cards. Each slot under the chamber is one try, against the dotted gold line: the better parent's GATE. Kardlings keeps the score of the try it keeps, so a try that did not beat both is a grey stub (never a made-up bar), and the kept one is the gold bar at its own GATE. A refusal can show its best try as a dim line, at or under the gold line. While it runs the chamber shows the two fusing; at the end it holds the fused card under a gold KEPT, or a red ribbon says REFUSED. Below it is the family tree: a fused card over its parents and theirs.

Builds and combos: proven decklists for real jobs

  
A job is a business's task with a bar to clear (the raid bosses are the first jobs). A build is a recipe of cards for a job: a kit (a lead card with its helper nodes and tools), a party (cards clearing a world boss together), a fusion (two parents), or a training run that makes a new, smaller student card from a teacher and data. A case is one example from the job's data (one patient's record, one loan file) that a build is scored on; held out means none of its parts learned from it. Its GATE is its score on those held-out cases (an AUC: 0.5 is chance, 1.0 perfect), the same score every card has. Once measured, a build has its own GATE, and the published rule buildLift says what it adds: its GATE minus the best GATE among its parts. Only a build with a lift above zero can be drawn as a combo; one below zero is drawn as an ANTI-COMBO, because parts that make each other worse are a lesson too. A re-run is another player measuring the same recipe again on their own device, signed with their own key; the card counts the keys. Which builds are combos (a margin, and re-runs by different players' keys) is the game's own sealed rule; the painter only refuses a combo the numbers cannot carry. Hand the card the game's verdict from its receipt and it draws exactly that verdict: a dip inside the game's margin is a plain build, with no ANTI-COMBO ribbon, so the card, the build sheet and the build book below always agree. A combo's name is never typed. With the game's verdict comes the game's name, its fielding cards' titles joined by ×, and the card checks it against the titles its parts carry before it wears it (cut short with … where the ribbon ends); with the receipt's build id, its sigil is grown from that id, the same rune the sheet and the book draw for that build. A recipe the game has not named wears a name grown from the recipe just as its sigil is, an adjective and a noun each picked from a fixed list of 32 (IRON, SILVER, GOLDEN… and WARDEN, ORACLE, ENGINE…), so there are 1,024 of those and no free text to police. Either way the first key to prove it is credited on the card by that key's face.

  
Try it: pick a kind and press Deal a recipe: the page picks a job, cards for each role, and their scores, and draws the build card. Each build has a sigil, a rune grown from its recipe (its kind, and each part's role and card, in order), so the same recipe always makes the same sigil and a famous combo is known on sight. The verdict is the game's to start with: the card is handed the same receipt the build sheet below reads, so it takes the game's sealed margin, the game's name and the build id's sigil. A training run is the exception: the game keeps its student only if it beats its sources, by its own training rule, so its card shows the sign of its lift. Pick None yet to see a card the game has not judged, where any lift below zero shows as an ANTI-COMBO, or Call it a combo yourself to watch the painter refuse one whose lift is not above zero (its name then grows from the recipe). A new deal goes back to the game's verdict, because a new recipe has its own lift. Reveal shows a combo's first appearance, COMBO FOUND. A part shown as ? is a card this device does not hold. In this demo the scores are dealt in your browser; in Kardlings they are measured, and every number re-runs.

  

    

      
      

    

    

      

      

      

      

      

      

      

    

  

  
The build sheet

  
The build sheet is a whole build on one wide picture, the size a link preview takes (1200 × 630), made to share: press Download the sheet below it to save it as a PNG. It reads the game's own records as they are: the receipt the game writes when it measures a build, and the proof its re-runs make (the paintSheet line in the code above takes both, unchanged).

  
Each part is a row: its Kardling (the pixel creature on its card), its title, its GATE alone, and what it adds. GATE is a score on held-out cases, the cases none of the parts learned from (an AUC: 0.5 is chance, 1.0 perfect); a part's GATE alone is its own score on the same cases the build was scored on, and what it adds is how far the build's GATE drops without it. The parts that field come first, numbered in the order of the build's name (the game names a build by its fielding parts' titles, joined by ×). A part the build does not need is benched: its row is dimmed, with BENCHED in place of its numbers. A ? in the HELD column is a part this device does not hold, so you can see what you are missing. On the right: the lift over the best part, the bar, how many held-out cases it was scored on, how many keys re-ran it, and the face of the first key that did. A key is a player's signing key (Ed25519, made on their own device); a re-run is another player measuring the same build again and signing what they got, and the game counts it proven once two different keys got exactly the same receipt.

  
The sheet draws the game's own verdict. COMBO: the build beats its best part by at least the game's sealed margin, a rule fixed before anything is measured (0.005 GATE today). ANTI-COMBO: it does worse than its best part by at least that margin. PLAIN BUILD: anything in between. The card above is handed the same verdict and name, so the two always agree. The sheet refuses a receipt whose numbers do not add up.

  
  

  

  
In this demo the receipt is dealt in your browser from the recipe above: what each part adds, the build's id, and its re-runs, signed by keys made from your key. Its verdict uses the game's margin. In Kardlings the game measures the build, and every number re-runs.

  
The build book

  
The build book is a job's leaderboard on one picture you can share (press Download the page below it for the PNG; in Kardlings it is the Build book panel of the builds screen). It lists every build the game has proven for that job, meaning two different players re-ran it on their own devices, each signing with their own key (a signing key made on their device), and got exactly the same numbers. A build's GATE is its score on held-out cases, the cases none of its cards learned from (0.5 is chance, 1.0 perfect). A combo beats the best of its cards alone by at least the game's sealed margin; an anti-combo does worse than the best of them by at least that margin. The combos come first, ranked by lift, the biggest first; then the anti-combos, marked ✗, the biggest drop first. A tie goes to the lower build id (a hash of the build's recipe, its cards, so the same cards always make the same id), so two devices always rank the same book the same way.

  
Each row has its rank, a small sigil grown from its build's id (the same build always wears the same sigil), its name (its fielding parts' titles joined by ×, cut short with … past 33 letters), its GATE, its lift (its GATE less the GATE of its best card alone), the face of the key that found it, and how many keys proved it. Six rows fit and the rest are counted. The head shows the job, its bar, and the best proven GATE against the bar; the page is framed in gold once that best clears it. The foot counts the combos, the anti-combos and the plain builds (proven, but neither a combo nor an anti-combo). It reads the game's own book for one job as it is. A page whose numbers or order do not add up is not drawn: the painter says which rule it breaks (a lift that is not the GATE less the best, rows out of order, a build counted twice).

  
  

  

  
In this demo the book is dealt in your browser for the job of the recipe above: its builds, their lifts, their finders (your key among them) and their keys. In Kardlings it is every build proven on your device, and every line re-runs.

Raids: the departments no card has cleared

  
Each boss is a department where no card has yet reached a GATE of 0.6 on cases it never saw: five in the hospital (admissions, clinical, pharmacy, history, discharge), bank credit, adult employer and credit billing. A boss's health is its distance to the bar, the published rule bossHealth(best) = max(0, 600000 - best) in millionths of GATE: the bar is full at chance (0.5) and empty at 0.6. When a card clears it the boss breaks apart, and the loot is that first card of its department. Click a boss below, then move the best score. GATE is a card's score on cases it never saw while it learned (an AUC: 0.5 is chance, 1.0 perfect); 0.6 is the bar a department must clear. Reaching the bar is clearing it: once a card reaches it, the boss falls for good and that card is the department's loot: the loot's title is that card's name.

The campaign: the raids as chapters

  
Each business is a chapter. First come its departments that no card has cleared (its department bosses, the nearest to the 0.6 bar first); last comes the business itself, its world boss, drawn as a crest bearing the business's icon. A world boss is cleared by a party of cards, at its best lone card's GATE plus 0.010, so its bar is its own. How it works

  
Nothing about a face is random and nothing about it is stored. The card's facts go in; the same bytes come out, every time, everywhere.

  
The flow, drawn from the code

  
Each box is a step paintArt takes in kardart.mjs, in order. The second line of each box is the workshop card above, traced live as it is drawn: change a fact there and watch it move here.

  
  
Each step, in words

  
    
    
  1. Check the factscheckFacts accepts exactly what a Kardlings card can hold and refuses everything else, with a reason.
    2. 
    
  2. Whiten the idThe 16 hex digits become 64 bits and pass through a 4-round Feistel network, so ids that differ by one digit look nothing alike. It is a bijection: no two ids share a genome.
    3. 
    
  3. Read the genomeEvery one of the 64 bits picks something: head, torso, legs, arms, crown, eyes, mouth, back, pattern, two colours and a 34-bit speckle.
    4.

    5. 
    
  5. Draw the worldThe theme paints the art window: synthwave in a neon front view, blockcraft in isometric blocks, pocket LCD in four dithered shades, Memphis in flat pop colour, blueprint as an engineering drawing with its dimensions. All integer geometry.

    7.

Why the arithmetic is integer-only

  
A card reader re-draws the face from the card's facts and compares the bytes with the picture; one differing pixel refuses a genuine card. Floating-point functions such as sin or pow are allowed to differ in the last bit between JavaScript engines, so the engine uses none of them: no trigonometry, no square roots, no random numbers, no clock. Curves come from integer tables and integer tests (a circle is dx*dx + dy*dy <= r*r), and the one division is a floor of two small whole numbers, which is exact everywhere. A test reads the source and fails the build if any banned call appears.

The white paper: a picture anyone can check

  

    
The problem
A collectible's picture is usually just a file stored beside its data. Nothing ties the two together: a card that says it is legendary can carry any image, an image service will not draw the same picture twice, and commissioned art costs staff time and fees for every new card. The picture is the part people look at, and it is the part nobody can check.

    
The idea
Make the picture a pure function of the facts. The engine takes a card's id, title, rarity, level, dataset, department and lineage, and nothing else, and draws its face. Then the picture works like a checksum anyone can recompute: re-draw it from the facts the card carries and compare the bytes. What you see is what the card carries, or the card is refused.

    
What makes it hold
Determinism everywhere: whole-number arithmetic only, one floor division, no clock and no random numbers, so every JavaScript engine draws the same bytes. A face for every id: the 64-bit id is whitened by a 4-round Feistel network, a one-to-one mixing, so two ids never share a genome and ids one digit apart look nothing alike. Looks that never move: a published theme is frozen and pinned by hash; a new look is a new theme id, so a new season never changes an old card.

    
How it is proven
Tests pin the bytes of every theme, refuse every bad input with a reason, and check that every fact changes the picture where that fact lives. A mutation witness then plants deliberate bugs in every kernel and requires the tests to catch each one, with none written off (the counts are in the blueprint above, and a test checks them against the witness). GitHub's runner repeats all of it on every push, and the button under The proof repeats the pin check in your own browser.

    
What it is not
It does not say who made a card or who owns it: that is the card's seal. It is not an image generator and holds no model: every Kardling comes from the code and the id. Taste is a judgement: the engine guarantees the same picture, not that you will like it, which is why a look you do not like is replaced by a new theme.

    
Why it matters beyond cards
Any product that shows a picture of a record (a badge, a certificate, a game item, a dashboard tile) can draw that picture from the record itself, on the viewer's own device, with nothing to host and nothing to send. Kardlings, the game these cards belong to, vendors this engine for exactly that: facts in, checkable bytes out.

  






  
For the people who decide

  
A collectible card product lives or dies on its picture. PixelWhisperer Kards turns a few facts about a card into a unique, rarity-coded, re-skinnable face, drawn on the viewer's own device in a fraction of a second: no art budget per card, no image service to rent, nothing that can drift between two machines.

How it is counted. Today: each card's minutes of staff time at the UK median hourly wage, plus any outside fee. With the engine: the hours your team still spends designing new themes, at the same wage, plus the electricity of every draw. Adoption: the hours to adopt, once, in the first year. Later years rise by UK inflation on both sides. The wage leaves out employer National Insurance and pension, so the saving is a floor, not a top end; the laptop figure is a processor's whole base power, so the engine's electricity is, if anything, overstated. Money is in pounds before VAT, as the basis states. If the answer comes out as a cost, that is the honest answer for those numbers.

Security, data protection and compliance

  
    
    
  • Network: none. The module imports nothing, and this page loads only its own files from this site and sends nothing anywhere; a test fails the build if either changes. The browser enforces it as well: the page's content security policy allows scripts, styles, fonts and images from this site only and no connection of any kind (no requests, sockets, frames, workers or form posts).
    • 
    
  • Data: the only inputs are a card's own facts (id, title, dataset, department, level, rarity, generation, parents). They are processed where the code runs and never sent anywhere by it. The engine holds no personal data of its own; what a card's title says is the card owner's choice, limited to 24 characters of letters, digits and a few marks.
    • 
    
  • Data protection (UK GDPR and GDPR): drawing a face adds no processor, no transfer and no store to your data map: the facts stay in the memory of the device that draws them, and nothing is kept once the picture is made. Your obligations for the card data itself are unchanged, because the engine never holds it. Nothing reaches the supplier either: there is no telemetry and nothing calls home.
    • 
    
  • Supply chain: one file, no dependencies, vendored byte for byte and pinned by SHA-256. On every push CI checks that the mutation harness is witness v0.6, by its tag, its commit and its hash, and re-checks every pin.
    • 
    
  • Hostile input: every entry point is total. Null, BigInt, circular objects, throwing getters and proxies come back as a refusal with a reason.
    • 
    
  • Audit: published themes are pinned by hash. If a theme's pixels ever change, the build fails.
    • 
    
  • Assets and trademarks: no third-party art, fonts or images: the font, icons and every Kardling are in the source. "Blockcraft" is a style name only.
    • 
    
  • Accessibility: this page works by keyboard, and every card on it carries a text description of its facts.
    • 
    
  • Certifications: none claimed. It is a library, not a service.
    • 
  


  
Deployment and roll-out

  
    
    
  1. Vendor kards/kardart.mjs byte for byte; record the commit and the file's SHA-256.
    2. 
    
  2. Call paintArt(facts, themeId, 384, 560) for each card's face and place it under your header band.
    3. 
    
  3. Store the theme id with the card. Readers re-draw from the facts and compare every byte.
    4. 
    
  4. For a new season, append a theme and its pins. Nothing else changes and no existing card is affected.
    5. 
  

  
The effort is one import and one call; you size it for your team in the calculator. A sensible pilot is one season's cards in one theme, with your card reader re-drawing every face it opens; a full roll-out is the same change, kept.

Risks, answered straight

  
    
    
  • Taste. The art is generated, and the last inch of taste is the owner's to judge. Themes are cheap to add, so a look you dislike is replaced by a new theme, not endured.
    • 
    
  • Frozen themes. A mistake in a published theme cannot be edited away, only superseded by a new id. That is the price of old cards re-drawing exactly.
    • 
    
  • Family resemblance. The 264 figure counts distinct genomes. Kardlings share one anatomy (a 9 × 14 × 7 voxel body), so expect relatives to look related; every one of 1,000 random ids was tested to give a different Kardling.
    • 
    
  • Not a seal. A face proves a picture matches its facts. Who made the card and who owns it is the card's seal's job.
    • 
    
  • Text limits. Titles and departments use a restricted alphabet and length, because nothing else can be printed.
    • 
    
  • Speed. A face is drawn by the device's own processor, not a server's, in the time the trace and the calculator above measure live on this device. A screen that shows many cards draws each once and keeps the bytes.
    • 
    
  • Supplier risk. None at run time: nothing calls home, so if the supplier stopped tomorrow every vendored copy would keep drawing the same bytes.

Adoption

  

    
For the Kardlings card

      
Vendor kards/kardart.mjs byte for byte at a named commit and call paintArt(facts, themeId, 384, 560) for the 384 × 560 area under the card's 16-row data band. To open a card, re-draw the face from the facts the card carries and compare it with the picture: if one byte differs, refuse it. A theme id on the card says which world to draw. The game view builds on the same kit: ui.mjs for the font, icons and key faces, estate.mjs for the home plot, arena.mjs for duels, raid.mjs for the bosses, gear.mjs for the kit, back.mjs for the back of every card, with its maker's mark, and fusion.mjs for the Fusion Lab; an item card is paintArt with a form.

    
To add a theme

      
A published theme is never edited, because old cards must still re-draw exactly. A redesign is a new id, for example synthwave-v2: append it to THEMES, run node tools/kards-pins.mjs synthwave-v2, paste its pins into kardart.pins.mjs, and let the witness prove it. The old themes' pins stay green.

    
For any build that wants collectible graphics

      
Give each thing an id and a handful of facts, call paintArt, and you have a face that is unique, rarity-coded and re-skinnable by changing one string. A new season is a new theme id, not a migration.

  

  
Why it spreads

  
Every card is one of 264 Kardlings, with its rarity visible at a glance, its parents on its face and a link that shows exactly the same card on any phone. Re-skinning is one click, so a new theme can make every existing card new again without invalidating a single one.

    Limits, said straight
    
  
      
    
    • A face proves a picture matches its facts. It does not prove who made the card or who owns it; the card's seal does that.
      • 
    
    • Sizes other than 384 × 560 (or any exact multiple of 192 × 280) pick the nearest pixel: legal and deterministic, but squashed or stretched, and the small print is unreadable below about 192 pixels wide.
      • 
    
    • The pixel font covers the characters a title and department may hold; nothing else can be printed, so nothing else is accepted.
      • 
    
    • A theme, once published, is frozen. That is the point, and also the cost: a mistake in a published theme is fixed by a new theme, never by an edit.
      • 
    
    • "Blockcraft" is a style name for blocky voxel art, "Pocket LCD" for a four-shade handheld look, "Memphis" for the 1980s design movement and "Blueprint" for the engineering drawing. None is affiliated with, or derived from, any game or product.
      • 
    
    • The arena draws the duel it is given: who hit, who missed and how it ended. Deciding a duel, or refusing one, is the game's job; this page's demo deals random cases. A raid shows GATE to four decimal places, measured in millionths.
      • 
    
    • A sealed card proves its face matches its record, not who made it: the Kardlings game checks the maker's signature. A sealed file saved again by another program stays face down until it is sealed again from its record.
      • 
    
    • I own functional correctness. The last inch of taste in the art is the owner's to judge.
