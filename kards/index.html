PixelWhisperer Kards · the DIGI card's art engine

Every card has a face only its facts can draw.

A DIGI card is a sealed picture that carries an ownable intelligence, one that grows as it proves itself. This engine draws that picture: a blocky voxel creature born from the card's own id, in the world its theme paints (neon synthwave, blockcraft islands, a four-shade pocket screen, Memphis pop, an engineering blueprint, and whatever is added next), with the title, level, rarity, dataset, lineage and id printed in a pixel font. It draws the game around the cards too: the back of every card with its maker's mark, item cards (apps, pwas, nodes, talkers, routers), the estate a player grows, duels in the arena and the raid bosses. It is drawn with whole numbers only, so any browser re-draws the same bytes, and a reader can refuse any card whose picture is not the one its facts make.

Built by Kar, the estate's resident builder, as a side build for PixelWhisperer. Powered by the Konomi architecture, created by Thomas Frumkin.

The workshop: make your own

Change any fact and the card is re-drawn from scratch. Roll a new id for a new creature. Nothing here is stored or sent anywhere; the link button puts the card in the address bar so you can share it.

Card backs: the maker's mark, face down

Every card game has a back, and a DIGI card's says who made it. The back is drawn in the card's theme: the theme's field and frame, the DIGI emblem, and the maker's mark: the face of the maker's Ed25519 public key (the same identicon as in the UI kit) in a medallion, with the key written short beneath it, and the card's edition number. The stars, ore, clouds and confetti in the field are thrown with the maker's own dice, so all of one maker's backs match and another maker's differ: a hand of one maker's cards is known face down. A card with no maker says UNSIGNED. The same back always draws the same bytes.

Try it: Roll a maker to make up a key, or paste a real one: a maker's public key is the key a DIGI player signs their cards with (YOUR KEY in DIGI), 64 characters of 0-9 and a-f. Change the edition, pick a theme. Untick Signed to see an unsigned back. Flip the card turns the picture over: the card in the workshop above on one side, this back on the other. Below, the same maker in every theme.

One maker, every theme

import { paintBack, checkBack } from './kards/back.mjs';
paintBack({ maker: publicKeyHex, serial: 123 }, 'synthwave-v1', 384, 560)   // { ok, px } | { ok: false, why }
// maker: the maker's Ed25519 public key, 64 lowercase hex; leave it out for an unsigned card. serial: the edition, 0 to 999999, or left out.
// The back is 192 x 280 logical pixels, scaled to the nearest pixel for any size from 64 to 1024: 384 x 560 is the DIGI card at 2 x.

What it refuses, and what a change can break. A key that is not 64 lowercase hex characters, an edition outside 0 to 999999, a theme it does not know and a size outside 64 to 1024 are each refused with a plain reason (the message under the picture above is that reason), and nothing throws. The scatter is seeded by the first 16 characters of the maker's key, and the identicon folds in all 64 (about 40 bits of pattern and colour, so two makers' marks rarely match; the key written beneath it tells them apart, and the key itself is what DIGI checks). Every theme's backs are pinned by sha256 in the tests, so no change to a published back lands silently: CI goes red until it is made on purpose.

Items: apps, pwas, nodes, talkers and routers

A card can be more than a scorer. Its form says what it is: an app is drawn as a window, a pwa as a phone with a bolt, a node as a server, a talker as a terminal with a speech bubble, a router (it picks, case by case, which of its owner's allies answers) as an antenna. Every theme draws the object its own way, from the item's own facts: its name, its form's icon, the source it was minted from, the gear slot it fits, its id and barcode, and a frame in the rarity its verified tier earns (prototype common, works uncommon, proven rare). A scorer card, which names no form, is drawn exactly as before, byte for byte. The form is one of the card's facts like any other: a card with a different form is a different card, with a different face.

The kit: node and tool slots

A card fields node slots (two at birth, three once uncommon, four from rare) and two tool slots. A node is another of its owner's cards, coupled with it; its slot shows the card and its measured worth on GATE in millionths (+19,727), or the card dimmed and hatched when it is not joined. A tool is an app item, framed in its tier; a tool never changes a score. The item above, when it is an app, sits in the first tool slot. The badge a card wears in a duel says how many of its node slots are fielded. Drawn by paintSlot and kitBadge.

import { paintArt, FORMS, TIERS, GEAR, itemFront } from './kards/kardart.mjs';
paintArt({ form: 'app', id, name: 'Churn Radar', source: 'divorcerbot', tier: 'works' }, 'synthwave-v1', 384, 560)   // { ok, px } | { ok: false, why }
// FORMS: scorer app pwa node talker router. TIERS: prototype works proven (common, uncommon, rare). GEAR: an app or pwa is a tool, a node or router an ally, a talker a voice.
// itemFront(form, id): the item as a 9 x 14 portrait, for an inventory slot
import { paintSlot, kitBadge, worthText } from './kards/gear.mjs';
paintSlot({ kind: 'node', card: { id, rarity }, worth: 19727 }, 'synthwave-v1', 112, 128)   // or joined: false; a tool: { kind: 'tool', item: { id, tier } }; empty: { kind }
kitBadge(fielded, slots, scale)                                     // the kitted overlay: { ok, w, h, px RGBA }

The estate: grow your plot

Every card a player holds is a tower on an isometric blockcraft plot, its trim in its rarity and its own creature on the sign. Tools are blocks, consented mesh links are cyan wires, and the districts still to come are fenced grey. The plot opens by a published rule: a district holding n blocks has tilesFor(n) = min(36, 8 + 2n) open tiles, so a new player starts with 16. The same holdings always draw the same picture, so a shared snapshot can be replayed and checked.

Try it: Add a card raises a new tower; Breed a new child adds a generation-1 card, standing in for one bred from two you hold, and marks it fresh, so its sign sparkles until the next child; Wire two cards joins two of your cards with a consented mesh link, a cyan wire; the slider sets how many tool blocks you hold; tick the snapshot to see the 1200 × 630 picture a shared link shows.

Holding items or swarms opens the full plot: nothing fenced, nothing coming. Tick Hold items, or add one: an app or a pwa stands as a tool block, a node as a dark server block with its lights, a talker as a terminal with a speech bubble, a router as an antenna. Form a swarm joins two to four of your cards in a consented team: it stands in SWARM as a stack of its members' blocks, wired to their towers. Every district opens by the same rule and is 6 × 6, so the rule holds to 36 tiles in all five. An item's top edge is trimmed in its tier's colour, and a new one sparkles. Holdings of scorer cards alone draw exactly as before.

import { paintEstate, estateStats, tilesFor } from './kards/estate.mjs';
paintEstate({ cards: [{ id, dataset, stage, rarity, generation, department?, fresh? }], wires?: [[idA, idB]],
              tools?: n, levels?: n, snapshot?: true }, 'blockcraft-v1', 1200, 630)   // { ok, px, scale } | { ok: false, why }
// a card: stage is its level, 0-99 (a tower grows a block every 25 levels); fresh marks a new child; department and generation are carried, not drawn.
// px: w × h RGB at the size asked for, each logical pixel a scale × scale block (480 × 320 is scale 2, 1200 × 630 is scale 3).
// snapshot: true adds a title band and a stats band (blocks, tiles, mesh links, and levels when given): the picture a shared link shows.
// The full plot: items: [{ id, form: 'app' | 'pwa' | 'node' | 'talker' | 'router', tier, fresh? }] and swarms: [{ id, members: [card ids] }] in place of tools.
// districts: ['scorer', 'tools', 'swarm'] draws only those districts, nothing fenced: what the DIGI game holds.
// names: { swarm: 'KITTED' } letters a district drawn with a name of your own, 1 to 8 of A-Z, 0-9 and space; nothing else moves.

The arena: two cards, one batch of cases

Two scorer cards face each other on the same batch of cases. On each case a card either hits (ranks it right) or misses; the side that hits where the other misses ranked that case better, and anything else is a tie. The scoreboard fills as the cases are decided: each side's hit or miss, and between them a block in the colour of the side that ranked the case better (grey for a tie). The latest case puts a tick or a cross beside each fighter, a rating badge sits over each, and the end is a WIN banner over the winner, a DRAW ribbon across both, or a REFUSED ribbon. The tally is published as duelScore, and the same duel always draws the same picture, so a replay can be checked.

Press Play the duel to watch it a case at a time, One case to step, New duel to deal another pair and batch. The badge over each card is its arena rating; the platform and badge colour are its rarity; the pips under the badge, when a card is kitted, are its node slots, lit for each one fielded. In DIGI a duel is decided by each card's AUC on the batch: the chance it ranks a case that is truly positive above one that is not (0.5 is a coin toss, 1.0 is perfect). Equal AUCs are a draw.

In this demo each card has a hidden hit rate for the batch and the cases are dealt in your browser; in DIGI the cases are real, and the AUCs decide the ending. The painter draws whatever duel it is given.

import { paintDuel, duelScore, checkDuel } from './kards/arena.mjs';
paintDuel({ left: { id, rarity, rating, title }, right: { id, rarity, rating, title }, cases: [[1, 0], [1, 1], [0, 1]],
            decided: 3, result: null }, 'synthwave-v1', 1200, 630)   // { ok, px, scale } | { ok: false, why }
// cases: [leftHit, rightHit] per case, 1 to 192. result: null while it runs, then 'left' or 'right' (WIN), 'draw' or 'refused'.
// duelScore(duel): { left, right, ties, decided, cases }, counting only the decided cases

Raids: the departments no card has cleared

Each boss is a department where no card has yet reached a GATE of 0.6 on cases it never saw: five in the hospital (admissions, clinical, pharmacy, history, discharge), bank credit, adult employer and credit billing. A boss's health is its distance to the bar, the published rule bossHealth(best) = max(0, 600000 - best) in millionths of GATE: the bar is full at chance (0.5) and empty at 0.6. When a card clears it the boss breaks apart, and the loot is that first card of its department. Click a boss below, then move the best score. GATE is a card's score on cases it never saw while it learned (an AUC: 0.5 is chance, 1.0 perfect); 0.6 is the bar a department must clear. Once a card reaches it, the boss falls for good and that card is the department's loot: the loot's title is that card's name.

import { paintRaid, bossHealth, BOSSES, bossSprite } from './kards/raid.mjs';
paintRaid({ dataset: 'hospital', department: 'admissions', best: 554000, attempts: 12 }, 'synthwave-v1', 480, 320)   // { ok, px, scale } | { ok: false, why }
// best: GATE in millionths, or null for no score yet. From 600000 the boss falls: pass loot: { id, rarity, title? }, the first card to clear it.
// bossSprite(key, scale): a boss's 32 x 32 sprite as RGBA, for a roster

The UI kit: the font, the icons, the key face

A DIGI screen is built from the same blocks as the cards. The card font becomes a real font, so labels stay selectable, accessible text; the dock and action icons are drawn in the same 16 × 16 cells as the dataset icons; and a key gets a face of its own.

The font: PixelWhisperer.ttf

LV 99 · GATE 0.874 ✓ KEPT → BEAT BOTH ≤ 2 (FRESH) 100% [OK] "RERUN IT!"

Above: real text in the font at 18px (two CSS pixels to a glyph pixel). Below: the same glyphs drawn as pixels by paintText.

At font-size: 9px × k each glyph pixel is exactly k CSS pixels, the line is one em and every character advances six pixels. A browser's rasterizer may still soften edges: Windows smooths vertical edges by about a third of a pixel, and a screen whose device pixels are not whole CSS pixels blends them. Where a heading must be pixel-perfect, draw it with paintText. Download the font · its CSS.

What a change can break. Nothing you have vendored. The glyph table, every icon, the identicon and the estate pictures are pinned by sha256 in the tests, so no change lands silently: CI goes red until a change is made on purpose and its pin moved in the same commit. Copy kardart.mjs, ui.mjs, estate.mjs and fonts/ at a named commit and your screens draw exactly those bytes until you choose to move. Start here

  1. Look. Pick a card in the gallery. Flip the theme through all five worlds, or show them side by side.
  2. Tinker. Open it in the workshop and change a fact: the title, the level, the rarity, a parent. Watch where each one lands on the card (the anatomy below shows the map).
  3. Take it. Download the PNG or copy the link. Every card is a pure function of its facts, so the same link shows the same card on any device.
  4. Play. Make an item card, hold items on your estate and watch TALKER open, play a duel in the arena a case at a time, and run a boss down to 0.6 in a raid. Every one of those pictures is drawn from its facts the same way a card is.
  5. Build with it. One import and one call draws a card's face, for any size from 64 to 1024 pixels:
import { paintArt, checkFacts, THEMES } from './kards/kardart.mjs';

const facts = { id: '3f9a1c7e5b208d46', title: 'Churn Hunter', dataset: 'telco', department: 'retention',
                stage: 34, rarity: 'rare', generation: 2, parents: [] };
const art = paintArt(facts, 'synthwave-v1', 384, 560);   // { ok: true, px: Uint8Array(384*560*3) } RGB rows, top to bottom
if (!art.ok) console.log(art.why);                       // bad input is a refusal with a reason, never an exception

Anatomy of a card

  1. Title in the pixel font, centred on the plate (at most 24 characters).
  2. The creature, generated from the id: symmetric, characterful, one of 264. The scene around it is the theme.
  3. LV and its 100-pixel bar: the levels earned by receipts (0-99), one pixel per level.
  4. Dataset icon and name (telco, shop, bank, adult, hospital, credit, custom) and the department below it.
  5. Rarity: the frame, the palette (grey, green, blue, purple, gold), the spelled name and the stars. Epic and legendary cards also get a night sky or more stars.
  6. Lineage: GEN and a tally (long bars are tens, short ticks are ones), then each parent's identicon, or GENESIS for a first-born.
  7. The id as #xxxxxxxx… and a barcode of all 64 bits.

How it works

Nothing about a face is random and nothing about it is stored. The card's facts go in; the same bytes come out, every time, everywhere.

  1. Check the factscheckFacts accepts exactly what a DIGI card can hold and refuses everything else, with a reason.
  2. Whiten the idThe 16 hex digits become 64 bits and pass through a 4-round Feistel network, so ids that differ by one digit look nothing alike. It is a bijection: no two ids share a genome.
  3. Read the genomeEvery one of the 64 bits picks something: head, torso, legs, arms, crown, eyes, mouth, back, pattern, two colours and a 34-bit speckle.
  4. Build the creatureA symmetric voxel model, 9 × 14 × 7. Always one connected piece, always with eyes.
  5. Draw the worldThe theme paints the art window: synthwave in a neon front view, blockcraft in isometric blocks, pocket LCD in four dithered shades, Memphis in flat pop colour. All integer geometry.
  6. Print the chromeTitle, LV bar, dataset icon, department, rarity, lineage and id in a 5 × 9 pixel font, then the rarity frame.
  7. Scale to the size askedThe face is a 192 × 280 pixel canvas. At the DIGI card's 384 × 560 each pixel is exactly 2 × 2. Other sizes pick the nearest pixel.
  8. Hand back RGB bytes{ ok: true, px }. The PNG writer is separate and also deterministic.

Why the arithmetic is integer-only

A card reader re-draws the face from the card's facts and compares the bytes with the picture; one differing pixel refuses a genuine card. Floating-point functions such as sin or pow are allowed to differ in the last bit between JavaScript engines, so the engine uses none of them: no trigonometry, no square roots, no random numbers, no clock. Curves come from integer tables and integer tests (a circle is dx*dx + dy*dy <= r*r), and the one division is a floor of two small whole numbers, which is exact everywhere. A test reads the source and fails the build if any banned call appears.

For the people who decide

A collectible card product lives or dies on its picture. PixelWhisperer Kards turns a few facts about a card into a unique, rarity-coded, re-skinnable face, drawn on the viewer's own device in a fraction of a second: no art budget per card, no image service to rent, nothing that can drift between two machines.

What each role gets

CEO

Every card is its own character, visibly rarer as it gets rarer, parents printed on its face, shareable by link. You get collectibility without commissioning art, and a new season is a new theme, not a rebuild.

CFO

The marginal cost of one more card's art is zero: it is drawn on the viewer's device. No per-image fee, no per-seat licence, no cloud bill for art. The case below is arithmetic on your own numbers, not ours.

COO

One module and one call. There is nothing to host, schedule or scale: no server, no queue, no storage, no dependencies. If a device can show a page, it can draw a card.

CTO and CISO

Pure integer code with no network access and no imports, in one file you pin by SHA-256. Deterministic: the same facts give the same bytes in any browser, so a reader can verify a card's picture by re-drawing it. Hostile input is refused, never thrown. Proven by tests, hash pins and a mutation witness in which every mutant is killed.

Security, data protection and compliance

  • Network: none. The module imports nothing and this page makes no requests; a test fails the build if either changes.
  • Data: the only inputs are a card's own facts (id, title, dataset, department, level, rarity, generation, parents). They are processed where the code runs and never sent anywhere by it. The engine holds no personal data of its own; what a card's title says is the card owner's choice, limited to 24 characters of letters, digits and a few marks.
  • Supply chain: one file, no dependencies, vendored byte for byte and pinned by SHA-256. CI re-checks the harness and the pins on every push.
  • Hostile input: every entry point is total. Null, BigInt, circular objects, throwing getters and proxies come back as a refusal with a reason.
  • Audit: published themes are pinned by hash. If a theme's pixels ever change, the build fails.
  • Assets and trademarks: no third-party art, fonts or images: the font, icons and every creature are in the source. "Blockcraft" is a style name only.
  • Accessibility: this page works by keyboard, and every card on it carries a text description of its facts.
  • Certifications: none claimed. It is a library, not a service.

Deployment and roll-out

  1. Vendor kards/kardart.mjs byte for byte; record the commit and the file's SHA-256.
  2. Call paintArt(facts, themeId, 384, 560) for each card's face and place it under your header band.
  3. Store the theme id with the card. Readers re-draw from the facts and compare every byte.
  4. For a new season, append a theme and its pins. Nothing else changes and no existing card is affected.

The effort is one import and one call; you size it for your team in the calculator.

Support and ownership

Built by Kar, the estate's resident builder, in the open repository. Vendoring means you hold the file: there is no runtime dependency on anyone. Updates arrive as new commits you choose to take, and because a published theme cannot change, taking an update never alters an existing card. Questions and defects go to the repository's issues.

Risks, answered straight

  • Taste. The art is generated, and the last inch of taste is the owner's to judge. Themes are cheap to add, so a look you dislike is replaced by a new theme, not endured.
  • Frozen themes. A mistake in a published theme cannot be edited away, only superseded by a new id. That is the price of old cards re-drawing exactly.
  • Family resemblance. The 264 figure counts distinct genomes. Creatures share one anatomy (a 9 × 14 × 7 voxel body), so expect relatives to look related; every one of 1,000 random ids was tested to give a different creature.
  • Not a seal. A face proves a picture matches its facts. Who made the card and who owns it is the card's seal's job.
  • Text limits. Titles and departments use a restricted alphabet and length, because nothing else can be printed.
  • Speed. About 25 ms for a 384 × 560 face on the machine that built it; the trace above shows the figure for your device, live. Draw once and keep the bytes.

The case for the board

Collectible, verifiable, season-proof card art at zero marginal cost per card, from a one-file, no-dependency, no-network component that is proven by tests, hash pins and a mutation witness instead of promised. The downside is bounded: it is a single file that you can delete.

Adoption

For the DIGI card

Vendor kards/kardart.mjs byte for byte at a named commit and call paintArt(facts, themeId, 384, 560) for the 384 × 560 area under the card's 16-row data band. To open a card, re-draw the face from the facts the card carries and compare it with the picture: if one byte differs, refuse it. A theme id on the card says which world to draw. The game view builds on the same kit: ui.mjs for the font, icons and key faces, estate.mjs for the home plot, arena.mjs for duels, raid.mjs for the bosses, gear.mjs for the kit and back.mjs for the back of every card, with its maker's mark; an item card is paintArt with a form.

To add a theme

A published theme is never edited, because old cards must still re-draw exactly. A redesign is a new id, for example synthwave-v2: append it to THEMES, run node tools/kards-pins.mjs synthwave-v2, paste its pins into kardart.pins.mjs, and let the witness prove it. The old themes' pins stay green.

For any build that wants collectible graphics

Give each thing an id and a handful of facts, call paintArt, and you have a face that is unique, rarity-coded and re-skinnable by changing one string. A new season is a new theme id, not a migration.

Why it spreads

Every card is one of 264 creatures, with its rarity visible at a glance, its parents on its face and a link that shows exactly the same card on any phone. Re-skinning is one click, so a new theme can make every existing card new again without invalidating a single one.

    Limits, said straight

    • A face proves a picture matches its facts. It does not prove who made the card or who owns it; the card's seal does that.
    • Sizes other than 384 × 560 (or any exact multiple of 192 × 280) pick the nearest pixel: legal and deterministic, but squashed or stretched, and the small print is unreadable below about 192 pixels wide.
    • The pixel font covers the characters a title and department may hold; nothing else can be printed, so nothing else is accepted.
    • A theme, once published, is frozen. That is the point, and also the cost: a mistake in a published theme is fixed by a new theme, never by an edit.
    • "Blockcraft" is a style name for blocky voxel art, "Pocket LCD" for a four-shade handheld look, "Memphis" for the 1980s design movement and "Blueprint" for the engineering drawing. None is affiliated with, or derived from, any game or product.
    • The arena draws the duel it is given: who hit, who missed and how it ended. Deciding a duel, or refusing one, is the game's job; this page's demo deals random cases. A raid shows GATE to four decimal places, measured in millionths.
    • I own functional correctness. The last inch of taste in the art is the owner's to judge.
